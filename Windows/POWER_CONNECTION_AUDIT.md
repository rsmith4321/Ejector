## Original before-fix inspection

Inspected source: **cf9e1a7**, with unchanged production behavior from the a7afd34 review checkpoint. This is an identified verification gap, not a reproduced hardware failure or an implemented fix.

`StorageNotificationWindow.WndProc` handles storage arrival/removal/configuration broadcasts (`0x219`) and busy end-session (`0x11`). Classic `DeviceWindow.WndProc` also handles the hotkey and those storage/session messages. Neither handles `WM_POWERBROADCAST` (`0x218`). `WindowsDiscovery.ConnectionChanged` increments the global epoch; `ConnectionVersions` changes its per-instance stamps on native device callbacks or monitor begin/disable. `StorageConnectionProof.Validate` deliberately accepts a changed global epoch when complete fresh inventory, protected topology and scoped stamps remain equal, so unrelated-device events do not interrupt transfers.

Microsoft documents suspend (`4`), automatic resume (`18`, every system resume) and user resume (`7`, following automatic resume after user interaction) in [WM_POWERBROADCAST](https://learn.microsoft.com/en-us/windows/win32/power/wm-powerbroadcast). Ordinary power-status (`10`) and power-setting notifications are separate events. Any implementation must distinguish these and keep message handling bounded. It must not change system power/display/lock settings or request actual suspend/resume as part of default tests.

Inference to verify: if connection tracking misses a period while suspended, accepting the old scoped stamp after resume could preserve an older review or completion authority. The source currently has no explicit power-boundary retirement. This does **not** prove that this laptop misses native device callbacks, or that an actual stale eject occurred. Actual sleep/wake/device acceptance was already an open parity gate.

Next focused work should first exercise the existing handlers with synthetic messages in an owned test window and capture before/after epochs/stamps/proofs. No power event may be sent to the real running preview or the OS. If the gap is reproduced, retire pre-boundary proofs in both interfaces, reject admission while suspended, require a fresh post-resume review, preserve a pre-existing tracking fault, and continue accepting unrelated-device events after fresh proof. Check that battery/charger status changes do not create a boundary. Include active generated transfer cancellation/refusal, retained originals/copies, stale completion refusal, fresh retry and registration/disposal ownership. Default tests must use fake device APIs/disposable files; any native message smoke must be separately opt-in/read-only.

Delivery contract follow-up: Microsoft's [RegisterSuspendResumeNotification](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-registersuspendresumenotification) accepts an owned window handle and returns a registration that must be unregistered; failure returns null. The existing storage-only registrations are not evidence of that power subscription. The more specific [automatic resume documentation](https://learn.microsoft.com/en-us/windows/win32/power/pbt-apmresumeautomatic) also excludes a sleep-to-immediate-hibernation transition on Windows 10 1507 and later. Synthetic managed message delivery proves only handler behavior. Any later registration implementation needs its own availability/failure/lifetime tests and real platform delivery evidence; do not infer Modern Standby or all hibernation transitions from the generic “every resume” wording.
