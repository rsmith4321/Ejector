## Review ownership

ReleaseView is the actual presenter used by WinUI. Native file/folder choices and inline restore confirmation capture one-use owner/action/epoch tokens. Another picker, worker, folder action or close is refused until the current choice/worker is terminal. Stop revokes delivery but retains a token-ignoring worker/picker's lifetime. Lost and regained activity cannot revive an earlier choice. Restore is a separate explicit action bound to exact presented backup ID/description; Keep current history cancels. Existing session/store guards retain protected signed restrictive history, neighboring settings and media, enforce fresh channel/replay/file identity and report uncertain publication honestly.

Worker completion does **not** present a result. The UI consumes a separate one-use delivery gate after its await, requiring current view epoch/latest request and the backend session's own presentation gate. Activity between completion and queued delivery, a newer request or closure refuses old delivery. Rejected terminal evidence is released only for that same latest terminal request; an old queued callback cannot cancel a newer active worker. Close-default ContentDialog uses inline confirmation to avoid a second dialog on the same XAML thread. [Microsoft's ContentDialog reference](https://learn.microsoft.com/en-us/windows/windows-app-sdk/api/winrt/microsoft.ui.xaml.controls.contentdialog?view=windows-app-sdk-2.0) documents XamlRoot, closing cancellation and dialog ownership. Actual keyboard/picker/rendering behavior remains unrun.

XAML failure revokes the view, then awaits the exact retained picker and worker before disposing the review/folders. Late rendering is disabled during that cleanup. The ordinary window/tray busy/close/Quit rules remain in effect. Folder open is read-only shell navigation, never executable launch or installation permission.
