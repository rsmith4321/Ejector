# Modern login and tray startup

Source `6d0b04b62b168d684e7c19a4dcc1e150cc25ebd4` connects the modern login draft and startup lifecycle to the existing strict Windows registration policy, preserving the separate icon/layout source `4a865b6`. Baseline Mac `384cb767ffbbb87ec5fe67f45d0b4d0ce324ad7c` SettingsView.swift and the classic StartupRegistration, StartupLaunch, StartupPresentation, Settings dialog, reopening and completion contracts were inspected. The full port still requires actual modern foreground, tools/LUT, disposable hardware and trusted distribution acceptance.

Settings reads login status without changing it. Launch at login starts off if no owned entry exists. A checkbox change or **Use this copy at login** is only a draft until explicit Save; Cancel/navigation publishes nothing. An existing canonical classic or other modern copy stays selected until explicit retarget, or explicit disable removes only the owned value. An unrecognized command/binary/expanded value stays intact and cannot be edited. The current-user 64-bit Run value remains `EasyEject.Windows`; no machine-wide policy, service, task, RunOnce, Windows enablement or security setting is modified. Windows Startup apps can disable or delay a registered entry; the app reports that limitation rather than claiming policy was overridden. Saving does not start a process or enable automatic imports.

Modern registration requires the exact local canonical `EasyEject.Modern.exe` name, quoted path and sole `--startup` argument within the existing length limit. Default classic policy still requires `EasyEject.Windows.exe` and treats modern commands as foreign. Enabling pins the exact executable and parent directories through publication. Snapshots bind policy and current executable, stale records refuse before writing, and exact readback must confirm the result. An uncertain applied write is reported honestly and never retried automatically. The one-use StartupEdit owns Save, refuses concurrent edit/cancel/duplicate workers and verifies the login choice captured before the independent settings writer. Settings may save even when login publication fails; the combined result reports both. An unchanged login choice is reread for current status without repairing a later entry.

The custom modern Main validates arguments before WinRT/XAML, initializes WinRT wrappers, claims the existing modern AppInstance key before creating a window and subscribes to redirected activation before UI startup. A secondary normal launch redirects a reveal; a secondary login launch exits silently. The thread-safe TrayStartupGate retains a normal wakeup received during initialization, starts monitoring once, coalesces reveals and revokes queued callbacks on shutdown. The window starts notifications/inventory independently of Root.Loaded, so a login launch does not require showing the window to monitor storage. Normal launch/tray reveal use the owned dispatcher reopening path. Root readiness is awaited only when an explicitly configured completion policy needs a visible dialog after verified work. No startup action automatically exports or ejects; automatic import remains its separate saved opt-in policy.

The entry point follows [Microsoft's Windows App SDK instance-management guidance](https://learn.microsoft.com/en-us/windows/apps/develop/launch/multi-instance-apps), including disabling generated Main and installing the dispatcher synchronization context. Gate tests prove delegate ordering and ownership, not actual WinUI no-flash behavior or native instance IPC.
