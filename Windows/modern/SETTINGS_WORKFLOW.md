# Modern Settings, shortcut and grouped card removal

Source `e6d4a1fb1255152ea89aaf7f15a78b952a9f6bba`, with navigation follow-up `43f47a25655ec9acca076fa105bb863e47af24ec`, connects the modern Settings page, Windows shortcut dispatch and grouped card-removal review. Baseline Mac SettingsView.swift/GlobalHotkeyManager.swift and Windows AppSettingsDialog/EditSettings, GlobalHotkey, BulkEjectPolicy/Service/Dialog and metadata-cleanup contracts were inspected. This remains a milestone of the full port, not complete Settings/lifecycle/foreground/hardware acceptance.

The scrolling Settings page has a fixed Save/Cancel footer and controls for notifications, metadata cleanup, warnings for other storage, debug logging, shortcut enable/letter and automatic release-check preference. All nine baseline letters are retained; Windows uses Ctrl + Alt + Shift. Editing affects only an owned draft. Enabling metadata cleanup requires a separate Cancel-default warning; stale, foreign, cancelled or replayed confirmations cannot enable it. Saving starts no import, cleanup, removal or launch-at-login change. An active Save owns its draft and disables controls/navigation/close/Quit; cancellation, second workers and edits are refused. Failed saves are consumed even if a record was durably written; reopen/read before a manual retry. Saved notifications/cleanup/warning choices feed the existing guarded operation services. Debug-enabled result/settings events append through the shared guarded local log; diagnostic viewing/clear and persisted issue presentation remain pending.

The Windows shortcut uses an owned invisible NativeWindow and the existing GlobalHotkey registration API. It starts off by default and registers only the selected supported chord if saved as enabled. Conflicts and unregister failures stay inactive and are reported without choosing another key. Dispatch checks exact ID/modifiers/key, coalesces pending requests, consumes each delivered callback once and checks busy/closed state again on delivery. Reconfiguration (even to the same key), a failed queue, destroyed window and shutdown revoke queued authority. A shortcut only opens the same fresh grouped confirmation as the button/tray; it never executes removal directly. Actual native registration/key input has not been exercised in this milestone; dispatch tests use fake APIs.

**Eject cards…** in the storage window/tray obtains fresh inventory and saved cleanup settings, lists all affected camera/emulator physical devices/volumes and defaults to Keep Connected. A one-use GroupedEjectReview freezes the selection and optional cleanup plans, invalidates affected import completion choices only after confirmation, and delegates to BulkEjectService. Existing group/partition identity, per-device connection stamps, reservations, sequential requests, veto/cancellation and final complete absence reconciliation remain authoritative. An accepted Windows request does not by itself mean safe to unplug. The result reports only currently verified absent devices; a partial veto preserves exact counts and remaining cards. Stop waits for the current boundary and prevents further requests. Ordinary media, indexes and device Trash stay outside metadata cleanup. The actual terminal result is retained before notification/result-dialog callbacks.

Settings page drafts, confirmation and workers participate in main-window/tray/navigation/busy rules. Defaults/profiles/history/tools transitions discard unsaved settings without publishing. Hidden/queued shortcuts cannot bypass a current Settings/profile/defaults review. General Settings changes do not suppress automatic imports or change import defaults/sharing preferences.
