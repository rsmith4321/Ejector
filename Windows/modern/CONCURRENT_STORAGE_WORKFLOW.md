## Contracts and integration

Mac baseline `384cb767ffbbb87ec5fe67f45d0b4d0ce324ad7c`, `EjectorApp.swift`, reserves manual removal through `DroneImportManager.reserveManualEject` and refuses a disk busy importing/ejecting. The tested classic Windows implementation already has `ConcurrentStorageState`, `ConcurrentEjectService`, per-physical-disk reservations and scoped connection proof. This milestone connects that policy to the modern interface; it introduces no parallel import, automatic export or automatic eject.

While an import, resumed import, exact saved-file verification or manually confirmed Quick Share worker is live, the modern window and tray may review safe removal or optional metadata cleanup of an unrelated device. Complete current inventory, continuous protected source/destination/sibling proof, an unreserved unrelated removal group and notifications are required. Source, destination, related sibling disks, opaque guards, unavailable tracking, stale/incomplete inventory, other dialogs and a second other-device review stay blocked. Manual refresh and passive inventory updates retain the selected volume and main transfer progress. Neither names nor an old menu item grant authority.

`ConcurrentStorageWork` owns the exact `Task` and activity token. Ready callbacks must match that still-live worker; completed, foreign and old callbacks cannot attach proof or drain newer work. Failure to obtain optional unrelated-device proof leaves the primary task owned and other-device actions unavailable. Drain refuses an executing primary, revokes new admission at terminal and retains the exact existing manual-review wait. A new primary cannot begin while that review is still open. Imports/resumes retain their held folders until that wait finishes; verification/sharing retain their terminal results before presentation. The sharing ready hook is optional, occurs only inside a manually confirmed operation after destination validation, and creates no tools/output or automatic action by itself.

`ConcurrentStorageReview` freezes one removal plan and optional cleanup scope, with Cancel default, one execution and its own cancellation source. The existing service revalidates primary and secondary proof, cleanup scope and target reservations before filesystem/native actions. Stop this device action is independent of Stop the main transfer. Close/escape while the worker is active requests secondary Stop and retains ownership until the exact worker is terminal. Accepted removal cannot be relabelled cancelled by a late Stop. Partial metadata counts/veto/failure are retained before UI callbacks; ordinary media remains outside cleanup scope. All new removal tests use fake native APIs and owned generated data.

The UI uses a single scrolling ContentDialog for confirmation, independent Stop controls, progress and terminal outcome. Its Close default never starts removal. The primary waits for that dialog to close before showing completion, preventing a second ContentDialog on the same thread. Microsoft documents that [ContentDialog permits one open dialog per thread and supports cancellable closing and button-click deferrals](https://learn.microsoft.com/en-us/windows/windows-app-sdk/api/winrt/microsoft.ui.xaml.controls.contentdialog?view=windows-app-sdk-2.0). The window's primary cancellation and counts are retained separately. Other-device outcome has a separate status line; failures retain a bounded issue even with notifications disabled and cannot be cleared by subsequent primary success. UI failure waits for the owned worker and releases the finished review in a finally block even if result/notification presentation fails.
