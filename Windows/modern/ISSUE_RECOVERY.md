## Contracts

Every modern View issue explicitly rereads `issue-state.json`, including when the previously loaded state was empty. IssueRecordReview retains the canonical directory lease for the entire prompt/worker, captures the folder's native identity, and freezes private single-link bounded strict JSON plus its hash/native file stamp. Returned payloads are copies. Save compares the exact reviewed previous record under ConfigurationWriter's exclusive hold and revalidates folder/live revision at every publication boundary. Changed bytes, deletion, addition, identical-byte replacement, different roots, moved/replaced folders and protected/aliased state refuse without overwriting foreign data. The automatic record/clear paths also compare their last confirmed folder/file snapshot; a successful operation cannot erase an externally changed issue. Existing malformed/unreadable records are retained.

Save actions are one use, including failures. Closing/reentry refuse while the worker owns the review, and the WinUI review waits for its exact worker before releasing the folder even if presentation fails. A frozen saver input cannot be changed through a caller alias. Confirmed readback is required; after-publication/readback failure remains an uncertain save, with no automatic retry or rollback claim.

IssuePersistenceState keeps the current explanation and attempted payload/live revision. A fresh manual review can recognize an already durable acknowledgement or clear without repeating it. A save that did not apply permits a fresh action. A later failure, including an identical-text/time payload with a newer in-memory revision, keeps attention and cannot be consumed by the earlier uncertain action. If current and persisted explanations differ, both are shown and only explicit **Save current explanation** replaces the newly reviewed saved record. That action preserves acknowledgement status and runs no media operation; a later separate Dismiss remains manual. An unreadable record offers a read-only live explanation with no writable review. Reopening after an invalid record has independently become valid still requires an explicit save for the unsaved explanation.

Restart loads only durable issue state. Unsaved in-memory explanations cannot survive a process termination; this milestone does not invent a second fallback store or claim otherwise. Actual application restart/foreground acceptance remains unrun.
