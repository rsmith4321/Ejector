# Windows direct distribution and manual updates

This is a reviewable delivery plan for the full Windows port. The current executable is an unsigned `0.1.0-dev` prototype. There is no approved Windows release channel, signing publisher, Windows package or public download. The new **Windows updates & installation** tray view gives manual instructions and read-only folder actions; it does not check releases, verify a downloaded package, download, install, replace or restart the app.

## Delivery and retained state

Deliver a versioned Windows x64 ZIP for Windows 11/.NET Framework 4.8, extracted into a folder owned by the user. Include `EasyEject.Windows.exe`, its `.exe.config`, approved release notes/licensing and authenticated verification information. Select the public version only when the release is approved. Do not use the Mac DMG/PKG/app, Sparkle appcast or Store assets as a Windows channel.

Keep application versions in separate folders so the previous folder remains available for rollback. Keep settings, enrolled profiles, defaults, exact last-20 batch history, selected tools, the user-supplied official LUT and diagnostics in the separately resolved `Profiles.Root`. The native guide displays the actual runtime folders rather than assuming the unpackaged `%LOCALAPPDATA%` path; packaged host redirection can change that path.

No FFmpeg/FFprobe installation or manufacturer LUT bundling is included. Their setup and every Quick Share action remain explicit. Startup remains off initially; installation does not create a registry entry. A user who already opted into startup must explicitly review the moved-copy registration when changing app folders.

## Manual install, update, rollback and removal

1. After an approved Windows release exists, verify its archive SHA-256 and trusted executable signature against its approved Windows publisher and authenticated download information. A familiar filename, matching version or any unrelated trusted signature is insufficient.
2. Before updating, finish or safely cancel work, close dialogs, and choose **Quit** from the tray. Closing the main window hides it and leaves work running. The guide cannot restart the app or cancel an import/removal request.
3. With the app stopped, make a settings-folder backup before upgrading. Extract the complete verified release into a new versioned folder, retain the previous folder, then manually start only the new copy. Review its version and saved choices.
4. To roll back, finish work and Quit the new copy, then manually start the retained previous version. It reads the same separate settings. If an older version refuses a newer format, review the earlier backup before any deliberate restoration; do not silently downgrade settings or overwrite changed state.
5. To remove the app, explicitly disable its own startup entry if enabled, finish work and Quit, then remove only the chosen application folder. Settings and imported media remain. Clearing settings is a separate deliberate decision.

The source busy/scan/dialog guard blocks opening the update guide during active work, including unrelated manual eject concurrent with a transfer. The disabled owner/owned modal checks cover native dialogs. Mac Sparkle's deferred relaunch timer is not used in this approved manual delivery direction: the Windows guide never queues installation or relaunch, and Close/Enter/Escape only closes it.

## Candidate validation and remaining channel work

The native trust primitive is implemented in `WindowsAuthenticode.cs`: held-file cached-only `WinVerifyTrust`, revocation/strong-signature policy, exact-zero success, verified-state signer evidence and exact approved subject/issuer binding. Candidate file review retains file/directory identity and compares full SHA-256 before/after trust. Its 23 fixture/native unsigned-refusal cases do not prove a trusted signed release. Later identity validation is not a replacement for rechecking the whole authenticated package's hashes.

`WindowsManifestTrust.cs` authenticates a bounded detached CMS data signature over exact bytes with an immutable body/hash snapshot. Crypto-only verification must also pass current-time cached native certificate-chain trust, code-signing usage and strong policy; embedded certificates remain in a temporary supporting memory store, with no ignored trust errors or imported roots. One embedded SHA-256/384/512 signer must match the explicitly approved publisher and the executable's exact leaf certificate. Twenty-one crypto/fake-chain/native-refusal cases pass; this does not prove an approved signed release. No publisher approval or channel is configured. The current-time manifest policy does not validate historical timestamp trust; publisher/provider lifetime and any necessary authenticated timestamp support must be resolved as part of the signing path before release.

`WindowsPackageReview` implements an already-extracted local folder review using those trust layers. Format 1 has exactly six ordinary files: `EasyEject.Windows.exe`, `EasyEject.Windows.exe.config`, `README.txt`, `LICENSE.txt`, `windows-release.json`, `windows-release.json.p7s`. The authenticated single UTF-8/no-BOM JSON object has exactly `format` (1), `application` (`EasyEject.Windows`), `platform` (`windows-x64`), canonical four-part `version`, lowercase 40-hex `sourceRevision`, and four `files` records with exactly `name`, positive bounded integer `length`, lowercase SHA-256 `sha256`. Payload names are the first four files; manifest and detached signature authenticate themselves through the signature rather than circular entries. Source revision is the approved publisher's signed attestation bound to payload hashes, not independently reconstructed build proof.

The reviewer retains file/directory identity and no-write/delete-sharing handles, checks every whole-file hash and exact inventory, x64 GUI/managed PE headers, native resource product/name/version and native read-only managed assembly/name/version/product/title/file/informational agreement, exact Framework 4.8 configuration and bounded UTF-8 documentation/licensing. Unknown/duplicate/trailing/typed/schema fields, aliases/reparse/extra/missing files, wrong versions/app/platform/PE/config and changed hashes refuse. It rejects extra named data streams while preserving bounded download `Zone.Identifier` metadata without treating it as approval. Revalidation rechecks complete hashes/inventory and both fresh trust roles. Twenty-four package cases and eight managed identity cases pass with **734/0** full tests; fake positive trust, patched disposable unsigned resources/managed metadata and fixture CMS signatures are not trusted release proof.

`WindowsArchiveReview` now reviews ZIP contents without extracting or executing. The release transport profile is a bounded single-disk/non-SFX/non-ZIP64 archive of exactly the six root files, Stored/Deflate, canonical ASCII names (UTF-8 flag optional), consistent ordinary DOS/Unix regular-file fields and signed/unsigned data descriptors. It rejects extra/comment/encrypted/split/link/directory/unsupported metadata, overlapping or inconsistent central/local records and trailing/prefix/gap bytes. It independently checks decoded counts/CRC and signed payload lengths/SHA-256, authenticating the embedded detached manifest with the same required approved-publisher/current cached native trust. The whole ZIP SHA-256 remains a computed held snapshot until an authenticated channel binds it. A valid contents result does not approve the executable: after manual extraction, a fresh held native-signature/package review must match exact manifest/signature/leaf signer. Twenty-six archive cases are included in the **760/0** final full build/test; actual native untrusted refusal is observed, positive trust is fake. Actual trusted archive/channel encoding and Windows manual-extraction/rollback compatibility remain release gates.

Remaining source work includes ZIP/archive hash binding, authenticated release channel/discovery/version comparison and read-only review UI. Actual source/build provenance, signing-provider lifetime/timestamps, accepted trusted artifacts and manual install/rollback/foreground/filesystem proof remain release gates. No Windows publisher/channel is approved or configured, so inspection cannot determine newer releases or become “up to date.” Keep validation separate from a user's manual Quit/extract/launch actions.

Use fakes and disposable fixture files for source tests. Read-only native unsigned/refusal evidence is allowed; a fake positive signer or synthetic executable is not trusted signing proof. Hold candidate file/directory identities through review and recheck before any subsequent action. Do not extract or execute a candidate merely to inspect it. Do not add automatic downloads, installers, relaunch timers, system-profile collection or silent registry changes.

## Release gates

Before preparing actual signed distribution artifacts, record the full source/parity audit, actual tools/official LUT conversion validation, foreground/DPI/notification/hotkey/login behavior, Ryan-identified disposable camera/card/reader/destination/filesystem and long-transfer/reconnect/cancellation/cleanup/removal/eject evidence. Then confirm the Windows signing identity/trust path and obtain any needed explicit account/cost authorization. Do not create signing accounts, spend money or change security policy as a shortcut.

Record the actual release commit, tool/runtime versions, resulting artifacts, hashes, approved publisher evidence and independent verification/rollback results. An unsigned development build or passing fixture count does not satisfy those gates. Publish a Windows channel/download only after explicit publishing authorization. Until then keep the Mac editions/website untouched and every channel state visibly unavailable.
